# ۳۸ ـ روش آزمون backend برای این تغییرات

[فهرست اصلی](README.md) · [نتیجه‌های واقعی](10-tests-and-validation.md)

## محیط صحیح

RSpec به gemهای گروه test و دیتابیس آزمون نیاز دارد. image slim تولید برای این کار مرجع کامل وابستگی‌ها نیست. فایل [persian.tests.Dockerfile](../docker/prod/persian.tests.Dockerfile) برای نصب گروه‌های مناسب روی build-base آماده شد.

پیش از اجرای تست، `RAILS_ENV`، نام دیتابیس، نسخهٔ Ruby/Bundler و source واقعی container را مشخص کنید. نصب موفق gem یا وجود tag قدیمی، همسان بودن کد فعلی با test image را ثابت نمی‌کند.

## انتخاب تست بر اساس تغییر

| تغییر | حوزهٔ آزمون |
| --- | --- |
| انتخاب زبان | localization feature و SetLocalizationService |
| نام نرم‌افزار | setting، seed و mail header |
| نمایش تاریخ | helperهای I18n و My work |
| تاریخ جلسه | مدل و فرم جلسه |
| reminder | component فرم مربوط |
| توضیح backup | worker مربوط |

فهرست مسیرهای اجرای ترکیبی ۶۱۳ مثال در فصل ۱۰ آمده است. برای اصلاح کوچک، ابتدا تست مرتبط را اجرا کنید و فقط در صورت تغییر جدید یا نگرانی حل‌نشده دامنه را گسترش دهید.

## تفسیر نتیجه

شمار مثال، failure، revision، image و دیتابیس آزمون را ثبت کنید. skip یا خطای setup را به‌عنوان پاس حساب نکنید. lint روی خطوط تغییر هم با پاس کامل lint کل repository فرق دارد؛ گزارش قبلی هر دو را جدا کرده است.

خطای وابستگی یا نبود helper مصرف‌کننده را ابتدا در محیط آزمون رفع و همان سناریو را تکرار کنید. برای سبز کردن تست، fixture را طوری تغییر ندهید که رفتار واقعی مورد انتظار حذف شود. اجرای `db:migrate` یا آماده‌سازی دیتابیس این فصل فقط برای محیط test است، نه نصب اصلی.
