## هدف preflight

قبل از توقف سرویس، باید معلوم باشد چه نسخه‌ای اجرا می‌شود، candidate کدام است و راه بازگشت از چه داده‌ای استفاده می‌کند. داشتن یک backup قدیمی یا tag همنام این پرسش‌ها را پاسخ نمی‌دهد.

| مورد | مدرک مورد نیاز |
| --- | --- |
| برنامهٔ قبلی | نسخه، image ID و edition |
| candidate | image ID/manifest و نتیجهٔ تمرین |
| Compose | project، فایل‌های واقعی و resolved config خصوصی |
| داده | نام/مقصد دیتابیس و پیوست‌ها |
| منابع | فضای کافی برای dump، restore و image قبلی |
| بازگشت | config و نسخهٔ قابل‌استفادهٔ دادهٔ قبلی |

در ارتقای ثبت‌شده، تفاوت 17.6 با 18 در این مرحله آشکار شد. تأیید اولیهٔ انتقال image به جای تأیید تغییر schema فرض نشد و تصمیم ارتقا جدا روشن شد.

## توقف محدود

وقفه فقط اجزای OpenProject را دربر گرفت. proxy و همکاری اشتراکی و writerهای پس‌زمینه و web طبق برنامه متوقف شدند تا backup نهایی با دادهٔ ثابت گرفته شود. PostgreSQL و cache برای dump و restore فعال ماندند.

ترتیب توقف و زمان لازم باید با سرویس واقعی و کارهای در حال اجرا سازگار باشد. توقف همهٔ containerهای میزبان یا `down` سراسری راه معمول این عملیات نیست.

## قبل از باز کردن دسترسی

migration، مقایسهٔ داده، health و probe داخلی هر دو زبان باید نتیجهٔ روشن داشته باشند. اگر بررسی هنوز شکست دارد، باز کردن proxy صرفاً برای پایان دادن به وقفه، مرحلهٔ پذیرش را دور می‌زند. علت شکست verifier را از شکست migration واقعی تفکیک کنید و تنها بررسی لازم را پس از اصلاح تکرار کنید.
