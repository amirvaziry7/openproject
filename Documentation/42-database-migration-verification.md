# ۴۲ ـ تطبیق داده در migration نسخهٔ اصلی

[فهرست اصلی](README.md) · [پشتیبان و بازیابی](12-backup-and-rollback.md)

## شمار ردیف لازم است، کافی نیست

دو جدول با تعداد یکسان می‌توانند محتوای متفاوت داشته باشند. در عملیات ثبت‌شده، snapshot تعداد و hash محتوای ردیف‌ها برای مقایسه به کار رفت. بازیابی cold پیش از migration با همهٔ ستون‌های snapshot تطبیق داده شد.

بعد از migration، ستون‌های مشترک قدیم/جدید مقایسه شدند و تبدیل ساختارهای شناخته‌شده جدا بررسی شد. مقایسهٔ ستون‌های مشترک به‌تنهایی حفظ اطلاعات ستون حذف‌شده را ثابت نمی‌کند؛ انتقال معنایی آن باید جدا کنترل شود.

| تغییر ساختار | کنترل مرتبط |
| --- | --- |
| workflow | transitionها در ساختار جدید و رابطه با type |
| project/type | ارتباط‌ها، نه فقط نام جدول |
| wiki module | فعال بودن ویکی در ساختار جدید |
| تنظیمات | تغییر مورد انتظار جدا از دادهٔ اصلی |
| `schema_migrations` | تغییر تعداد/نسخه طبیعی است |

## نتیجهٔ واقعی

۸۲ migration اجرا شد و تعداد ثبت‌شده از ۲۰۸ به ۲۹۰ رسید. داده‌های اصلی مقایسه شدند و ارتباط project/type، ۲۳۴۴ transition و حالت ویکی تأیید شدند. metadata شمار migration ابتدا در verifier به‌اشتباه تغییر غیرمنتظره شمرده شد؛ آن کنترل اصلاح و تطبیق دوباره موفق شد، نه اینکه SQL migration شکست خورده باشد.

## روش گزارش

برای هر مغایرت بنویسید آیا ردیف حذف شده، جدول rename شده، ستون به رابطهٔ تازه منتقل شده یا دادهٔ جدید سیستمی ایجاد شده است. تغییر count به‌تنهایی را حذف داده نام ندهید و تغییر schema را نیز با یک count برابر بی‌خطر اعلام نکنید.

این بررسی‌ها نتیجهٔ snapshot همان عملیات‌اند. اگر بعداً دادهٔ جدید یا plugin متفاوتی اضافه شده، تمرین قدیمی جای بررسی candidate بعدی را نمی‌گیرد.
