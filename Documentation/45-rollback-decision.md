# ۴۵ ـ تصمیم بازگشت و داده‌های بعد از cutover

[فهرست اصلی](README.md) · [دستور دقیق rollback](12-backup-and-rollback.md)

## چه نوع مشکلی رخ داده است؟

| نوع مسئله | مسیر تصمیم |
| --- | --- |
| asset قدیمی یا cache | ابتدا image، fingerprint و منبع asset بررسی شود |
| مشکل هم‌پایه بدون schema جدید | تعویض image می‌تواند کافی باشد، پس از بررسی |
| شکست تغییر schema | image قدیمی را مستقیم به schema جدید وصل نکنید |
| مشکل پس از ثبت دادهٔ جدید | ابتدا حفظ و تطبیق نوشتن‌های بعد از backup |

داشتن گزینهٔ rollback به معنی لزوم استفاده از آن برای هر خطای ظاهری نیست. علت و دامنهٔ مشکل و هزینهٔ داده باید مشخص شود.

## مسیر آمادهٔ این استقرار

نسخهٔ recovery روی schema 17.6 باقی مانده و برنامهٔ واقعی قدیمی با آن boot شده است. helper هنگام بازگشت از دیتابیس ۱۸ نیز dump می‌گیرد و به مقصد recovery تغییر اتصال می‌دهد؛ دیتابیس و پیوست فعال ۱۸ حذف نمی‌شوند.

## مرز مهم

قبل از باز شدن دسترسی عمومی، snapshot قدیمی می‌تواند با نقطهٔ توقف writerها تطبیق داشته باشد. بعد از باز شدن، کاربران ممکن است رکورد تازه ثبت یا رکورد قدیمی را ویرایش کنند. snapshot قدیمی آن فعالیت‌ها را ندارد و نگه داشتن dump جدید، merge خودکار محسوب نمی‌شود.

به همین دلیل helper برای بازگشت پس از cutover تأیید صریح می‌خواهد. این متغیر تأیید، جای بررسی دادهٔ جدید را نمی‌گیرد. دستور کامل و کنترل pointer/checksum فقط در فصل ۱۲ نگهداری شده تا نسخه‌های متناقض دستور تکثیر نشوند.

## بعد از تصمیم

اگر بازگشت انجام شد، مقصد دیتابیس فعال و backup jobهای دارای نام hardcode بررسی شوند. تلاش دوباره برای نسخهٔ ۱۸ بعد از کار کاربران در نسخهٔ برگشتی، تصمیم مهاجرت دادهٔ جدید دیگری است؛ رفت‌وبرگشت بدون تطبیق، هر دو شاخهٔ داده را ناسازگار می‌کند.
