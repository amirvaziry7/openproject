## هدف

این الگو برای تغییرات بعدی است و گزارش اجرای انجام‌شده محسوب نمی‌شود. با پر کردن آن، تفاوت بین کد بررسی‌شده، artifact ساخته‌شده و محیط واقعاً آزموده‌شده روشن می‌ماند.

## مشخصات تغییر

| فیلد | مقدار مورد نیاز |
| --- | --- |
| تاریخ/مسئول | زمان واقعی اجرا و مسئول |
| مسئله | نشانه و اثر روی کاربر |
| scope | component، locale، محیط و فایل‌ها |
| baseline | نسخه، commit و schema قبلی |
| revision جدید | commit و status working tree |
| artifact | tag، Image ID، manifest و در صورت انتشار registry digest |
| داده | نوع تغییر schema/فایل و نیاز پشتیبان |

## جدول اعتبارسنجی پیشنهادی

| بررسی | اجرا شد؟ | محیط و نتیجه | مدرک بدون secret |
| --- | --- | --- | --- |
| ممیزی ترجمه | تکمیل شود | تکمیل شود | تکمیل شود |
| تست مرتبط backend/frontend | تکمیل شود | تکمیل شود | تکمیل شود |
| فارسی/انگلیسی و موبایل | تکمیل شود | تکمیل شود | تکمیل شود |
| دادهٔ ذخیره‌شده و ISO | تکمیل شود | تکمیل شود | تکمیل شود |
| build و هویت image | تکمیل شود | تکمیل شود | تکمیل شود |
| پشتیبان و آمادگی بازیابی | تکمیل شود | تکمیل شود | تکمیل شود |

اگر بررسی انجام نشده، صریحاً همان را بنویسید؛ خانهٔ خالی یا عبارت «باید پاس شود» نتیجهٔ موفق نیست. خطای قبلی و خطای جدید را جدا ثبت کنید.

## تحویل عملیاتی

نام فایل‌های Compose واقعاً مصرف‌شده، override فعال، سرویس‌های تغییرکرده و مقصد داده ثبت شوند. برای rollback، تفاوت snapshot با دادهٔ جدید و نیاز reconciliation نوشته شود. فایل خصوصی یا dump در گزارش عمومی پیوست نشود.

در پایان، لینک فصل‌های مستندات مرتبط و موارد باز را اضافه کنید. برای یک اصلاح کوچک، جدول را متناسب کوتاه کنید؛ هدف قابلیت بررسی و تکرار است، نه تولید ادعای آزمون یا زیاد کردن تعداد فایل‌ها.
